## 승인된 연구 정책

- 공식 `selective_rewrite`는 온라인과 같은 원 질의 대비 채택 판정을 사용한다. 공식 run에서 실제 LLM 실패로 휴리스틱 후보가 생기면 원 질의를 유지하고 실패를 기록한다. 정상 후보의 채택 규칙을 공유하며 온라인의 기존 장애 처리 계약을 보존한다.
- 새 `gating_effect`는 같은 재작성 정책으로 `ungated`, `rule_only`, `full_gating`의 고정 스냅샷을 비교한다. 기존 직접 메모리 실험은 명시적 ablation으로 재현할 수 있게 유지한다.
- 답변 평가는 우선 Java의 최종 검색 결과를 사용한다. Python의 현재 추출형 답변과 점수 계산을 유지한다. 온라인 답변 생성기를 평가하는 실험은 별도 설계로 다룬다.
- 실제 모드 매핑 교정과 새 공식 실험 정책은 [03](03-research-evaluation.md)에서 시행하고 결과에 정책 버전을 기록한다. 기존 공식 이력의 설정과 점수는 원본 그대로 조회할 수 있어야 한다.

## 모든 작업의 동등성 기준

| 경계 | 확인할 결과 |
| --- | --- |
| 검색·재작성 | 같은 fixture와 설정에서 메모리 범위·순서, 후보·최종 질의, 채택 여부·사유, 청크 순서·점수, rerank·RRF 입력과 출력 |
| 외부 모델 | 같은 입력에서 provider·endpoint·실제 model, system/user 메시지, JSON 형식, 생성 파라미터, timeout·retry·fallback 순서 및 최대 호출 횟수 |
| API·저장 | 상태 코드, 기존 DTO와 오류 속성, JSON 누락/null 규칙, 조회 이력, 실패 시 이미 저장된 온라인 trace, 평가 요청의 `NONE` |
| 연구 | 스냅샷·데이터셋·검색/모델 설정의 재현성, 순위 지표·Anchor 평가 입력, legacy 이력 재조회, 실험 artifact·작업 완료 계약 |

모델 출력의 변동과 구현 차이를 구분하려면 기록된 요청·응답 fixture나 가짜 provider에서 위 결과를 먼저 비교한다. 외부 모델을 쓰는 소규모 확인에서는 동일 설정과 호출 수, 지표·지연 변화 및 실패 분포를 기록한다. 수치 변동의 설명 없이 기존 경로를 전환하지 않는다.

## 후속 에이전트 실행 방법

1. 활성 작업 문서 한 개와 선행 단계의 증거를 읽는다. `.codex/AGENTS.md`와 루트·대상 디렉터리의 `index.md`·`progress.md`를 확인하고, 변경할 진입점과 보존할 계약을 구체적으로 명시한다.
2. 운영 경로를 건드리기 전에 재현에 필요한 fixture를 추가하거나 기존 테스트를 확장한다. 영향받는 backend·Python·Admin 소비자 테스트를 작은 범위로 실행한다.
3. 기능별 패키지와 역할을 유지한다. HTTP 경계는 DTO·advice, SQL은 repository, 모델 SDK와 HTTP 전송은 gateway에 둔다. 설정 해석, 순수 정책, 프롬프트 생성, 응답 조립은 해당 기능의 작은 컴포넌트에 둔다. 같은 필드를 여러 진입점에서 다시 해석하거나 여러 종류의 정책을 한 서비스에 모으면 변경을 다시 나눈다.
4. 각 단계는 독립적으로 검증하고 되돌릴 수 있게 마친다. 대상 `progress.md`와 루트 `progress.md`에 변경 범위, 검증 명령과 결과, 남은 조건을 적고 [작업 진행표](progress.md)를 갱신한다. 이전 단계가 검증되지 않았으면 그 사실을 인계한다. Spring AI 전환 시 미검증 조합은 기존 실행 경로를 사용한다.
